# 冰面复冰 · 冰场用水峰值预测

北湾冰上中心按场次预测复冰耗水，检查每次补满水箱之间的峰值，并据此签报冰车班次。

## 业务场景

北湾冰上中心是虚拟场馆，有一块主冰、一块教学冰和八名运维人员。水票抄进设备室账本，冰时表另由教务负责。交班时容易漏算调场后的复冰次数，直接引用昨日日均值会滞后于用水上升，拆段补水也常没有留够空档。系统将冰时单、水票和水箱规格串入同一班次，输出可追溯的备水量和签审状态，供值班冰车司机执行。

| 模块 | 页面 | 动作 |
|---|---|---|
| 场次调度 | 冰时安排 | 按冰面和班次登记冰时单、时段、复冰次数并检查重叠 |
| 实测计量 | 复冰计量 | 登记现场总升数、实际复冰次数和票号，检查连续记录 |
| 班次预测 | 预测回测 | 比较 Holt 与前日基线，生成分段用水证据 |
| 交接签报 | 班次签报 | 调整冰时和补水空档，重算后签审并锁定班次 |

|---|---|---|

## 工作日示例

1. 2026-11-23 08:00，录入员检查明天西岸主冰三个冰时单 SK-216、SK-222、SK-228，共安排六次复冰。
2. 08:15，核对东侧教学冰漏记的 WTR-1117 票。补录 3 次复冰、447 升后，连续计量日重新满足回测要求。
3. 09:00，主冰提交 11 月 10 日至 23 日的用水历史。留末四天 Holt 的平均绝对误差是 0 L，前日值的误差是 2 L。
4. 09:10，按每次 180 L 备水，一次加满后连续作业的峰值为 1080 L，超过 820 L 水箱，复核拒签。
5. 09:20，录入员试在 08:55 自由滑冰前补水，距上一场结束仅 5 分钟，系统拒绝该排程。
6. 09:35，将 SK-228 调到 09:10–10:30，登记开场前补满。旧预测被标记为过期。
7. 09:45，重算得到两个区段 720 L 和 360 L，两个值均低于容量。
8. 10:00，复核员确认新预测并签报。交接页面显示该版证据，签后冰时锁定。

## 预测口径

按各日总用水除以实际复冰次数形成 L/次序列。最近 12 天必须连续，最长使用 21 个连续计量日，最后一笔计量距计划日不得超过三天。Holt 加性趋势系数为 α=0.65 、β=0.25，初始趋势取首两日差值；用末 4 日逐日的一步预测与前一日实际值比较 MAE，平手采用前日值。获胜模型用全段历史预测目标日，按冰面设置增加预留并向上取整。每个满箱段用水等于含余量的每次备水量乘以该段的预约复冰次数。

## 签报后的水票更正

1. 复核员在对账页确认表码差后，系统用更正后的水票自动重算该冰面所有**尚未开工**的已签班次。
2. 重算峰值高于原签报峰值时，班次转为 `suspended`：停用时间、停用原因、原签报峰值和抬高后的峰值一并留存，交接页显示“暂停执行”。
3. 录入员调整冰时或补水空档、重新提交重算，再登记补单（引用某个重算版本并写明补排说明）。
4. 复核员签署补单才放行。签署时若补单引用的不是最新水票或调整后的冰时（并发更正、再次改排），或峰值超过水箱容量，补单退回 `returned` 并记录原因，班次保持暂停。
5. 同一张水票以相同结论重复复核不会再次重算，也不会重复挂起；改判为不同结论会被拒绝。停用记录按次留存，交接页可查历次原签报、停用原因、补单与当前可执行安排。


## 启动

```sh
cp .env.example .env
docker compose up --build -d --wait
docker compose exec -T backend python -m scripts.seed_demo
```

前端 http://localhost:18291，FastAPI 文档 http://localhost:19291/docs，数据库宿主端口 17791。端口和种子用 `.env.example` 中的环境变量配置。可单独启动 Compose 的 db/redis 供本地开发，在 backend 下安装依赖，设置 `DATABASE_URL`、`REDIS_URL`、`JWT_SECRET` 后运行 `uvicorn app:app --reload` 及 `python worker.py`。收尾运行 `docker compose down -v --remove-orphans`。

| 服务 | 技术 | 职责 |
|---|---|---|
| frontend | Nginx、HTML/CSS/JS | 场次时间线、计量、回测和签报 |
| backend | FastAPI、psycopg | API、身份、版本、排程与签审 |
| worker | Python | 回测和容量评估 |
| db | PostgreSQL | 冰面、冰时、水票、预测和签报关联 |
| redis | Redis | 登录限流和 worker 健康协作 |

`backend/schema.sql` 定义约束；`backend/domain.py` 管理 API 和模型；`schedule.py` 约束冰时和补水；`forecast.py` 完成验证与计算；`signing.py` 处理签报后停用与补单放行；`rink_seed.py` 定义演示数据。前端业务在 `frontend/ice.js`。角色和任务枚举在 `backend/core.py`、`frontend/base.js`；预测方法和签报状态在 `backend/schema.sql`、`backend/forecast.py`、`backend/domain.py` 和 `frontend/ice.js`。

## 巡检、机组与计量对账

- **冰面巡检**记录六区冰厚和沟槽，按单区及全场厚差签审；缺点或损伤阻止放行，修整单可关联复检。
- **机组派车**以最新放行巡检、冰面面积和场次空档为输入，在同机组跨冰面的已占时段之间找连续作业窗。每次复冰 8 分钟，补水再加 15 分钟。原冰时变化后撤回旧派车再安排。
- **表码对账**用水表跨度含回零计算实际用水。超过 5% 与 10 L 中较大的容差后提交复核；确认表码差会保留原票、加记修正用量并使未签预测失效。

`backend/migrations/` 采用增量结构，已有水票、预测和已签班次保留。签报后的水票更正流程见上文；`tests/test_correction_flow.py` 覆盖停用、补单退回与放行，运行前需可用 PostgreSQL（默认 `postgresql://app:pw@127.0.0.1:55432/business`，可用 `TEST_DATABASE_URL` 覆盖）。
